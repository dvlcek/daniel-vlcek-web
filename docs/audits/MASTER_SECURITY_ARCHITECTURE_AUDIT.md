## Executive verdict

The candidate is a credible premium landing page with a substantial native booking application. Retain Next.js App Router, React, Prisma 7, managed Neon and the existing visual identity. A rewrite, microservices, a CMS and a database move are not justified.

**Public release remains blocked.** No P0 vulnerability was established. Important P1 gaps remain in session termination, administrative request guards, booking recovery and operational acceptance. Most urgently, the actual Vercel production deployment predates A2: local RC1 protections must not be described as live protections. Recommend protecting existing public booking writes through an explicitly reviewed operational change while preparing a new accepted release. No such restriction was applied in this audit.

For the next 6–12 months recommend **Option C: Next.js on the intended Linux VPS, with a separately supervised worker using the same codebase, and Neon retained**. This is a recommendation subject to operational gates, not a statement that a VPS is inherently safer. See [blueprint](../architecture/VPS_MIGRATION_BLUEPRINT.md), [expansion](../strategy/WEBSITE_EXPANSION_PLAN.md) and [roadmap](../strategy/EXECUTION_ROADMAP.md).

## 4. Authentication and authorization assessment

Single-owner password authentication; no usernames, account directory, registration, recovery, user roles or multi-tenant boundaries. Account enumeration is largely inapplicable; generic login error avoids exposing a user list. Environment password is compared with timingSafeEqual after length check; there is no password hash store or enforced password strength. Prefer a managed identity/MFA solution or a small established authentication library over expanding bespoke password logic; no auth migration is implemented here.

Server authentication occurs before admin page data queries (`admin/page.tsx:280–331`) and in all five administrative mutation handlers. Admin IDs are scoped to a single all-powerful operator, so the absence of tenant filters is not a demonstrated IDOR. Add roles/ownership only when another principal or tenant is introduced. Proxy is a launch gate, not an auth boundary.

Admin cookie: HttpOnly, production Secure, Path=/, SameSite=Lax, seven-day lifetime. It lacks __Host prefix and backend termination. Booking cookies are stronger: 32 random bytes, hash-only persistence, per-attempt name with production __Host prefix, HttpOnly/Secure/Strict, one-hour lifetime. Expiry and ownership are rechecked using DB clock and FOR UPDATE inside reservation transactions. Advisory transaction locking protects initial same-attempt creation without an existing row. These A2 controls remain intact.

Management links are bearer capabilities, not proof of email ownership. Raw initial token hash and derived HMAC token are booking-bound; absent/incorrect IDs/tokens return the same 403. Fragments avoid server request/referrer query disclosure and are removed from browser URL, then stored in sessionStorage (`ManageBookingClient.tsx:124–190`). XSS would still threaten JS-readable storage. Customer/API responses omit lead PII and token hashes. No payment/account verification claim is made.
